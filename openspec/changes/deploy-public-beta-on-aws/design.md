# Design

## Context

See [proposal.md](proposal.md). The Vite build already emits a static SPA, service worker, and WEBU chapter files. `src/server/app.ts` is a transport-independent Hono app, but `src/server/listener.ts` starts a local HTTP server, uses `localDatabase()` (which rejects non-loopback endpoints), and uses an ignored API.Bible development response cache. The existing DynamoDB repository accepts an injected document client and table name. The repository currently has a GitHub remote and no production AWS or GitLab deployment configuration. The reference `../wcc-av-docs-infra` contains an S3/CloudFront SPA rewrite function, not the reader's API Lambda; its public bucket, broad methods, and `uri += '/index.html'` rewrite are unsuitable for this reader.

## Goals / Non-Goals

**Goals:** Keep one application/API origin; preserve current local operation and provider limits; make initial provisioning, secret setup, deployment, and rollback reproducible; minimize direct secret access and provider calls during verification.

**Non-Goals:** A second public environment, user authentication, provider quota scanning, changing Scripture contracts, or moving existing local development to AWS.

## Decisions

### 1. Two CloudFront origins and explicit SPA routing

Use a private S3 REST origin with Origin Access Control for the default behavior and the regional API Gateway HTTP API as the ordered `/api` and `/api/*` behaviors. CloudFront owns this split before any rewrite: all API paths select API Gateway; all other paths select S3. Set only GET/HEAD on the static behavior. Attach a CloudFront viewer request function to that behavior: rewrite `/` and recognized extensionless reader routes (`/<day>`, `/<day>/(psalm|proverbs)/<chapter>`, and optional verse/intro segment) to `/index.html`, while preserving their query strings; preserve requests for real static paths and files. Use explicit routes rather than a blanket 403/404-to-200 response, which would turn missing JS, WEBU JSON, or images into HTML. Set immutable long caching for hashed assets and versioned WEBU files; use revalidation or short caching for `index.html`, `sw.js`, and the manifest so updates propagate. Set the API behavior to HTTPS origin access, disabled edge caching, and forward the query strings needed for reading-day/time-zone cache policy. Preserve the `/api` prefix through an HTTP API `$default` stage and proxy route. Do not forward the viewer `Host` header to API Gateway.

The reference function's directory-style rewrite (`uri += '/index.html'`) targets directories with their own index files. This SPA has one root `index.html`, so its valid deep links must rewrite to that root file. The API Lambda uses Hono's [AWS Lambda adapter](https://hono.dev/docs/getting-started/aws-lambda); the CloudFront function performs only URI routing. AWS recommends [OAC for private S3 origins](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/private-content-restricting-access-to-s3.html).

### 2. Dedicated zone with external parent delegation

Use one Terraform deployment root and one GitLab-managed state (`terraform/`, `beta-app`). For the first deployment, `terraform/main.tf` enables only `modules/dns`; the `modules/app` block and application outputs stay commented out. Apply once, then add the hosted zone's four name servers at the `beckyandzac.com` parent DNS authority. After delegation resolves, uncomment `modules/app` and its outputs in the same files and apply again. This creates ACM validation records, CloudFront A/AAAA aliases, and an ACM certificate in `us-east-1` only after DNS is ready. The deployment role does not need parent zone rights. A backend-free `terraform/iam/` root calls the deployment-policy module to render, validate, and review policy documents for the externally created GitLab role; it does not create or edit that role. Preserve the zone and static bucket against accidental destroy. This follows Route 53's [subdomain delegation](https://docs.aws.amazon.com/Route53/latest/DeveloperGuide/dns-routing-traffic-for-subdomains.html) and CloudFront's [us-east-1 certificate requirement](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/cnames-and-https-requirements.html).

### 3. Node Lambda entry point and production DynamoDB

Extract shared construction of chapter services and content revision from the listener. Keep the local entry point's loopback client and local response cache. Add a Node-compatible Lambda entry point using `hono/aws-lambda` and an AWS SDK DynamoDB client with the default regional endpoint and execution role credentials. Package the Lambda with Bun targeting Node, pinned runtime version aligned with mise, and a deterministic ZIP. Terraform creates an on-demand table with `pk` string key and TTL on `expiresEpochSeconds`; grant Lambda only the repository operations required by the chapter cache. The Lambda runs outside a VPC so it can reach DynamoDB and providers without NAT infrastructure. Existing provider and cache semantics stay inside their current modules. No Lambda timer is required: repository operations already perform bounded maintenance on access, and DynamoDB TTL removes expired rows asynchronously.

### 4. Lambda environment variables for provider configuration

Use the existing server environment names `API_BIBLE_KEY`, `API_BIBLE_CSB_ID`, `API_BIBLE_NIV_ID`, `API_BIBLE_NLT_ID`, and `CROSSWAY_KEY` in Lambda. The user enters them as protected, masked, hidden GitLab CI variables scoped to the beta deployment; the pipeline passes them as sensitive Terraform inputs to the Lambda environment configuration. Validate that every required value is present and that the complete Lambda environment stays below the [4 KB limit](https://docs.aws.amazon.com/lambda/latest/dg/configuration-envvars.html). The handler reads values directly from `process.env` and does not fetch a secret during invocation or cold start. Rotation means changing the protected variable and deploying a new Lambda configuration.

This choice removes runtime lookup latency and the Secrets Manager charge. It also means provider values are stored in GitLab's variable store, Lambda configuration, and the GitLab-managed Terraform state even when Terraform marks inputs `sensitive`. Restrict GitLab project/state access, prevent state or saved plans from becoming public artifacts, avoid shell tracing and commands that print environment values, and grant AWS Lambda configuration access only to trusted roles. Do not imply that Terraform's `sensitive` flag removes values from state; [HashiCorp documents that state and plan files can contain secret inputs](https://developer.hashicorp.com/terraform/language/manage-sensitive-data). GitLab recommends protected, masked, hidden variables and cautions that masking alone cannot prevent a malicious pipeline from reading them ([GitLab variable guidance](https://docs.gitlab.com/ci/variables/)). No provider values enter browser assets, tracked files, or ordinary test fixtures.

### 5. GitLab OIDC, managed state, and release sequencing

Make `https://gitlab.com/zwing99/for-the-day` the canonical repository and use protected `main` and `beta` deployment environment. The user creates the AWS IAM OIDC provider for `https://gitlab.com` and a narrowly scoped deployment role independently. Set token audience to `sts.amazonaws.com`; pin the role trust to `project_path:zwing99/for-the-day:ref_type:branch:ref:main` and the project's stable `project_id` and `namespace_id` claims. The numeric IDs were read from the GitLab project. Publish a reviewed AWS permission policy covering Terraform resources, role pass-through for the Lambda execution role, Lambda configuration, code uploads, and CloudFront invalidation. The trusted deployment role can read the Lambda environment and the GitLab app state, so it must be restricted to the intended project and operators. GitLab CI requests an ID token and exchanges it through STS for temporary role credentials; no IAM user keys are stored in GitLab. GitLab's [AWS OIDC guide](https://docs.gitlab.com/ci/cloud_services/aws/) documents these conditions and exchange.

Configure the deployment root with the HTTP backend against GitLab-managed state `beta-app`. CI uses its short lived `CI_JOB_TOKEN` through `TF_HTTP_*` environment variables for state read/write and the GitLab lock/unlock endpoints. Do not put the token in a backend file, Terraform variable, saved plan, or artifact; reinitialize each job with its own token. GitLab handles state encryption, version history, and locking, so no separate AWS state bucket is needed. Restrict project membership and state access because users with sufficient project rights can download the app state and read provider values; disable public pipeline artifacts if the repository is public. Keep any app plan generated with secrets out of CI artifacts. GitLab documents the [state backend and CI authentication](https://docs.gitlab.com/user/infrastructure/iac/terraform_state/).

GitLab CI on protected `main` serializes beta releases, runs repository checks and build, then offers a manual plan and a single manual apply job against the same `terraform/` root and state. For the first deployment, the checked-in `main.tf` has only the DNS module enabled. After parent delegation resolves, uncomment the app module and outputs; the same plan/apply jobs then deploy the app. App applies sync static files with cache metadata, invalidate entry documents, and expose a provider-free verification job. Retain matched release artifacts and S3 static object versions so a prior API ZIP and static build can be restored together. Make GitLab the canonical remote and keep GitHub synchronized as a second remote.

## Risks / Trade-offs

- **Parent NS delegation or certificate validation is delayed** → Keep only the DNS module enabled for the first apply, then enable the app module only after the NS records resolve; display exact nameservers and validation state in the runbook.
- **CloudFront deployment serves mixed API/static revisions briefly** → Keep API contracts backward compatible, publish immutable static files before switching the entry document, and keep prior release artifacts for rollback.
- **Public API can consume provider quota** → Keep the repository's bounded cache, disable edge caching that could violate reporting, set conservative API Gateway throttles and CloudWatch alarms, and measure traffic before changing limits.
- **GitLab variables, Lambda configuration, and Terraform state contain provider values** → Limit project, state, pipeline, and Lambda configuration access; hide and protect variables; avoid saved plans and secret-bearing logs.
- **Terraform role is externally managed** → Provide a precise IAM trust/permission example and a preflight check that catches missing permissions before release.
- **Rotated provider values require a deployment** → Update the protected GitLab variable, run the release pipeline, and verify the new Lambda configuration without printing it.
- **Direct API Gateway URL remains reachable** → Treat it as the same public API; do not claim CloudFront is its sole access control. Rate limits and safe API errors apply at the gateway and application.

## Migration Plan

1. Push the repository to `https://gitlab.com/zwing99/for-the-day`, protect `main` and `beta`, and prepare the external GitLab OIDC role. Record the project and namespace IDs for the role trust.
2. With only `modules/dns` enabled in `terraform/main.tf`, run the manual plan and the single manual apply. Add its output nameservers at the parent DNS service. After delegation resolves, uncomment `modules/app` and its outputs in `terraform/main.tf` and `terraform/outputs.tf`.
3. Enter the provider keys and edition IDs as protected, masked, hidden GitLab variables; verify their presence without printing values, then uncomment and apply the app module in the same root.
4. Run the GitLab release pipeline. Verify health, shell, direct deep link, static WEBU asset, TLS and DNS, and route behavior using no provider calls. Only an explicitly budgeted manual smoke check may request licensed content.
5. For rollback, redeploy the previous retained Lambda ZIP and static build, restore entry documents, and invalidate their CloudFront paths. Keep the DynamoDB table and hosted zone intact; do not destroy provider cache or DNS as part of a code rollback.
